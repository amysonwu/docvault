# 许可协议选择说明（License FAQ）

本项目采用 **AGPL-3.0-or-later**。这份文档解释「为什么是它」「商业上会不会有麻烦」「不想用 AGPL 怎么办」。

---

## 1. 为什么选 AGPL-3.0 而不是 MIT / Apache-2.0

文档管理系统天生是**网络服务**：用户通过浏览器访问，代码不落到用户机器上。
这正是 GPL 的盲区：别人可以把你的代码改成 SaaS 卖出去，一行都不回馈。

AGPL 第 13 条补上了这个口子：

> 如果修改后的程序通过网络与用户交互，必须向这些用户提供获取对应源码的机会。

对我们的场景，这条带来两个效果：

| 效果 | 说明 |
|---|---|
| 有 | 有人拿它改成付费网盘对外运营，必须公开他的修改 |
| 有 | 员工在公司内网使用不构成「对外提供」，无需开源任何东西 |

**关键点：内部自用不触发开源义务。** 这是最常见的企业顾虑，担心是多余的。

---

## 2. 企业常见的四个问题

**Q：我们公司内部部署给 500 人用，要开源我们的定制吗？**
不需要。AGPL 的触发条件是「通过网络向**外部**用户提供服务」。公司员工、外包驻场人员在自己的内网里使用，属于组织内部使用。

**Q：我们在系统里接了自己的 OA / 单点登录，这些改造要开源吗？**
对系统本身的修改需要按 AGPL 提供源码（当你对外提供服务时）。你自己的 OA 通过 API 与它交互，不构成衍生作品。

**Q：能给客户做私有化交付吗？**
可以，这正是本项目的目标场景。交付时把源码（含你的修改）一并给对方就行。对私有化项目来说这通常不是问题，反而常是甲方主动要求。

**Q：我们做法务审核，AGPL 一律不许用，怎么办？**
见下面第 4 节：换协议，或买商业授权。

## 3. 商业授权（Commercial License）

如果你需要以下任一项，可以联系作者获取商业许可：

- 闭源分发、闭源二次开发，不愿承担 AGPL 开源义务
- OEM / 白标：把 DocVault 嵌入自己的产品对外销售
- 需要书面的知识产权声明、免责条款、SLA 支持

> 商业授权与 AGPL 并行（双许可）：社区版继续 AGPL，商业客户按合同获得豁免。有意向请开 GitHub Issue 说明需求。

## 4. 想把项目改成 Apache-2.0 / MIT

**前提：你必须是版权持有人**（或获得全部贡献者同意）。本项目采用 DCO 而非 CLA，
贡献者保留各自版权，所以换协议要征得主要贡献者同意。这件事建议在项目早期就定下来。

操作步骤（版权持有人自助）：

1. 替换 `LICENSE` 文件为 [Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0.txt) 全文；
2. 全局替换源码头部的 SPDX 标识：
   ```bash
   # Linux / macOS
   grep -rl "AGPL-3.0-or-later" --include="*.py" --include="*.html" . \
     | xargs sed -i 's/AGPL-3.0-or-later/Apache-2.0/'
   ```
3. 更新 `README.md`、`NOTICE`、`THIRD_PARTY.md` 中的许可表述；
4. 在 `CHANGELOG.md` 记录协议变更（旧版本仍按旧协议，不可追溯撤销）。

**取舍提醒**：换成 Apache-2.0 后，别人可以把你的代码做成闭源 SaaS 且不回馈。
如果这不是你担心的场景（比如你主要靠交付服务而非软件本身获利），Apache-2.0 会让企业客户更省心。

## 5. 贡献者的授权范围

提交 PR 即表示你同意：

- 你的贡献以 AGPL-3.0-or-later 授权给本项目及其他使用者；
- 你授予维护者一项非独占、永久、不可撤销的许可，允许在**未来更换协议时**继续使用你的贡献（用于双许可或协议迁移）。

这条写在这里是为了避免将来「换协议需要联系 200 个贡献者」的窘境。若不接受，请在 PR 中明确声明，我们会在合并前单独沟通。
