# 路线图

> 这个项目目前一个人维护。下面的顺序按「不做就会挡路」排，不按功能看起来酷不酷排。
>
> 有一条原则不变：AI 能力必须能跑在内网。需要把文档传到外部服务的功能，不会做成默认路径。

## v0.2 先让这东西能被长期使用（计划）

现在它能跑，但只是「能跑起来」。别人拿去部署会遇到三件事：升级会断，因为表结构靠 `create_all`，我加个字段老库就报错；坏了查不出，数据库有记录而磁盘没有块，只能靠人翻日志；外部接入只能靠登录态，脚本和第三方系统没法安全接。

这三件不解决，功能加再多也没人敢用，所以先把地基补上。顺序如下：

| 顺序 | 事项 | 为什么排这个位置 |
|---|---|---|
| 1 | Alembic 迁移 | 后面每个版本都要改表。压着不做，v0.3 加索引表就只能让用户手写 SQL。已有部署做一次 baseline stamp，之后随版本自动升级 |
| 2 | 存储完整性巡检 | 对账数据库清单与磁盘实际块，输出缺失与孤儿报告。块库是这套系统的资产，「备份可恢复」得能验证，不能靠假设 |
| 3 | 对象存储后端（MinIO / S3） | 前提是先抽出 `StorageBackend` 的 list/stat 接口。存储统计、GC、离线包现在直接扫本地目录，得一起改走接口，不是加个实现就完 |
| 4 | 大文档预览加速 | 首屏懒渲染 + 转换结果按版本缓存。验收口径：200 页 docx，同版本第二次打开不用重新转换，首屏 1 秒内 |
| 5 | OpenAPI + 个人访问令牌 | 让脚本和第三方系统接入，不共用登录态 |
| 6 | 审计报表导出 | 按人、按文档、按时间导出 CSV。改动集中在查询与导出，适合第一次参与的人 |
| 7 | 移动端适配 | 列表、预览、分享页在手机上可用。不做原生 App |
| 8 | OnlyOffice 镜像瘦身 | 裁掉用不到的字重和语言包。注意这需要自建镜像，官方镜像动不了，维护成本要算进去 |

## v0.3 编辑与阅读时的本地 AI（计划）

本地推理走 Ollama / vLLM / llama.cpp，模型文件放自己的机器上。界面上会标明「本地模型」，并给管理员一个总开关，可以整体关掉。

- **写作补齐**：选中段落做续写、改写、精简、扩写、转正式语气。结果先给建议，接受后才写入
- **表格补全**：只用于模板类表格（登记表、清单、空模板），按表头续行。数字类单元格一律要求逐格确认
- **打开即摘要**：长文档给要点卡片、待办提取、风险提示
- **可追溯**：AI 产生的修改与人工修改一样进版本链，可 diff、可回滚，标注 `AI 辅助`

有一处需要先验证：OnlyOffice 的修订模式能否由程序写入建议。它的修订功能主要面向人工操作，plugin API 能做到什么程度要试；如果做不到，就退回「建议块浮层 + 人工确认」，不影响上面这些能力。

## v0.4 把文档库变成可检索的知识库（计划）

- **索引**：对选定空间或目录建索引（按块切、算向量）。向量库是可选组件，Qdrant 容器或内置轻量检索都行；没部署时自动降级为关键词检索，不额外增加必需中间件
- **增量**：新版本只处理变化的块，不重建整库
- **引用**：每个回答都能回到文档、版本、段落，点一下跳原文
- **权限**：检索结果按现有权限内核过滤。这一条最难也最关键，过滤必须放在检索层，不能放在展示层
- **成本**：向量化用本地 embedding 模型，CPU 也能跑，但十万级文档的首次索引要按小时算。入库是异步任务，不挡上传
- **跨版本解读**：说明这一版比上一版改了什么、影响哪些章节
- **文档加工**：多份文档合稿（周报转月报、方案转评审稿），公文模板填表生成，从库里挑段落拼装并保留出处。产出是普通 docx，照常进版本链

## v1.0 企业环境与稳定承诺（计划）

1.0 的门槛不是功能齐，是接口稳、升级不炸：OpenAPI 冻结，迁移覆盖所有历史版本，有向后兼容承诺，并且真的演练过一次从 0.4 升到 1.0 的路径。

| 方向 | 事项 |
|---|---|
| 身份 | OIDC / LDAP / 企业微信 / 钉钉扫码，组织架构同步 |
| 高可用 | 多副本 app + 外部对象存储 + 数据库主从，备份恢复演练常态化 |
| 合规 | 水印策略（按人、按密级）、下载审批、DLP 外发管控、审计留存策略 |
| 集成 | 电子签章、扫描件 OCR 入库（本地 OCR）、WPS 私有化与 Office Online Server 适配 |
| 多租户 | 租户隔离、配额、租户级审计与报表 |

多租户这里有个取舍：单库多租户要给权限内核和几乎所有表加租户维度，改动面很大；如果需求集中在「几套独立环境」，用多实例加独立库更划算。等真实需求出来再定。

## 更远的构想（未排期）

- **文档健康度**：巡检「三个月没更新但被频繁打开」的文档，提醒责任人
- **版本语义命名**：从变更内容推断版本含义（小修、结构调整、结论变更）
- **跨文档一致性检查**：同一套指标在多份报告里数字不一致时告警。v0.4 的跨版本解读是两版对比，这个是跨文档巡检
- **离线包**：把某个目录打成加密离线库，带到无网环境查阅

## 不做的事

划清边界，避免方向漂移，也省得有人提了需求却等不到回应。

- 不做 SaaS 托管版。只交付能私有部署的代码，我不运营云服务
- 不做原生移动 App。移动端只做响应式网页
- 不内置公有云 AI。不提供「一键调用某云厂商大模型」的默认路径
- 不做 BPM 审批引擎。审批只到文档粒度（下载、外发），不替代 OA 工作流
- 不把 Redis、消息队列、K8s 变成运行前提。向量库也是可选
